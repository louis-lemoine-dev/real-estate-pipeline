## Overview

A diff-aware pipeline that scrapes ParuVendu listings and DVF transactions into Supabase, generates AI-backed investment insights (grounded in real historical comparables) for listings matching fixed criteria, and syncs them into Louis's existing Notion investment-triage workflow. Serves two goals at once: an actual home-buying tool for the Toulon/Var region, and a portfolio piece demonstrating a real, closed-loop, AI-augmented data engineering system. Tracked in its own dedicated Notion roadmap, separate from the Python & Dev Roadmap. Since 8 November 2026 the work continues in Claude Code (VS Code extension); the context files in this repository replace the claude.ai chat Project.

**State in one paragraph:** Phases 1, 2 and 3 are done. Phase 3 finished on 4 November 2026: the DVF transactions of all twelve communes (125,353 rows, sales from 2014-01-02 to 2025-12-31) are stored in Supabase, and a second full load changed nothing, which proves the refresh is repeatable. The ParuVendu side (listing ingestion, price history, delisting) is built and was verified on real Supabase with simulated days, but the `listings` and `price_change_events` tables are empty: it has never run on a real scrape, and nothing yet orchestrates the daily flow (Phase 7). When this file was written `main` was at PR #30 (`5a42611`) and 193 tests passed. Next is Phase 4 (market analysis dashboard). Louis still has to set the Notion Status/Done fields on 3.5.1–3.5.3 and step 3.5, and the Scope of 3.5.0.

- **Connection string: Session pooler (port 5432), not Direct connection.** Direct defaults to IPv6 and needs a paid IPv4 add-on on incompatible networks; Session pooler behaves like a normal persistent connection and stays on the free tier. No special pool config needed for session mode.
- Credentials in `.env` (gitignored) + `.env.example` (committed, redacted). Connection verified via a `scratch/` script running `SELECT 1`.
- **Supabase MCP connector** scoped via a custom URL (`?project_ref=<project-ref>&read_only=true`) rather than the default org-wide read+write directory connector. It is read-only; `execute_sql` is available for SELECT queries and is how real-database results are verified. All writes go through the project's own committed scripts and code.

**3.2 — Schema Design — done**
- **3.2.1 — Mapped `Listing`/`Transaction` dataclasses to tables.** Every column type chosen deliberately: `numeric` (not `float`) for money/surface columns to avoid rounding drift in `price_per_m2` — **except ParuVendu's `price` and `price_change_events.old_price`/`new_price`/`delta_eur`, which are `integer`** because the source only ever yields whole euros (`transactions.price` is `numeric`); `text` for every identifier that merely looks numeric (`listings.id`, `commune_code`, `property_type_code`); `bigint` for `transactions.id_mutation` (genuinely `int` at the source). `amenities` is `text[]`. `first_seen_at`/`last_seen_at timestamptz` were added to `listings` beyond the dataclass. **Amended (PR #25): `transactions.price` is now nullable** (migration 0004). Live `transactions` columns (verified 3 Nov 2026): the 13 `Transaction` fields exactly (`id_mutation`, `date`, `year`, `price`, `is_vefa`, `nature_mutation_code`, `nature_mutation_label`, `property_type_code`, `property_type_label`, `surface_bati`, `surface_terrain`, `rooms`, `commune_code`); `price` and `rooms` are nullable, everything else NOT NULL. The three derived columns the cleaning step adds (`price_per_m2`, `is_single_residential_unit`, `is_market_transaction`) do not exist in the table.
- **3.2.2 — `price_change_events`** is an append-only log (one row per detected change), not a mutable column. Surrogate PK. A first sighting is not an event (enforced via `not null` on old/new price). Verified in 3.4.3: the real table has only a plain index on `listing_id`, no uniqueness, so several events per listing are allowed.
- **3.2.3 — Keys, delete behaviour, indexes.** Natural PKs for `listings`/`transactions`. FK `price_change_events.listing_id → listings.id` is `ON DELETE RESTRICT` (nothing deletes listings; delisting only marks them). Composite index on `transactions (commune_code, date)`; single-column index on `price_change_events.listing_id`.
- **3.2.4 — Applied to Supabase.** Versioned migrations in `db/migrations/` (`0001_initial_schema.sql`, `0002_enable_rls.sql`, `0003_add_delisted_at.sql`, `0004_make_transactions_price_nullable.sql`), applied via the committed `scripts/apply_migration.py` (transactional; uses the shared `get_engine()`; usage: `poetry run python scripts/apply_migration.py db/migrations/<file>.sql`), never via the dashboard SQL Editor. **The script splits the file on every `;`, so a semicolon inside a migration comment can break it** (a `;` at the very end of a comment line is harmless). RLS enabled with no policies as future-proofing. No migration-tracking table yet (deferred until ordering strains).
- Delivered via PRs #13 and #14.

**3.3 — ParuVendu Diff-Aware Ingestion — done (code)**
- **3.3.1 — Diff logic (PR #15; amended in #16 and #21).** `classify_listings()` tags each scraped listing new / unchanged / modified and spots stored listings confirmed gone. "Modified" is price-only. Delisting is confirmed only after a second consecutive miss (implemented as elapsed time since `last_seen_at` ≈ 1.5× the daily scrape interval, not a counter column), and `check_run_sanity()` stops a collapsed scrape before anything is classified. Migration `0003_add_delisted_at.sql` added `listings.delisted_at timestamptz null`. Amended: #16 made it carry every original column through (instead of trimming to id/price); #21 made it refuse a scrape missing any `Listing` column (`LISTING_COLUMNS`, defined once in `models.py`, validated here because this is the only place scraped and stored data are still separate).
- **3.3.2 — Insert path (PR #18, plus #17).** `insert_new_listings()`: one batched INSERT in one transaction, retried on dropped connections, failing fast on integrity errors. Built on the shared `get_engine()` (`common/db.py`, `pool_pre_ping=True`). Verified end to end on real Supabase including the `text[]` amenities column. Lesson recorded on its Notion page: `.where(pd.notna(df), None)` silently leaves NaN in a float64 column, so a missing value can reach Postgres as NaN, not NULL.
- **3.3.3 — Update path (PR #21).** `update_listings()` refreshes every listing seen again (not only modified ones: a fresh `last_seen_at` is what makes the delisting rule trustworthy), writing the price-change event first, in the same transaction, then updating. Atomicity proven by test. The retry loop was centralised as `run_in_transaction()` in `common/db.py` and now serves all write paths (constants `DB_MAX_RETRIES=3`, `DB_RETRY_BACKOFF_SECONDS=1`, deliberately separate from the DVF+ client's). A manual check on real Postgres exposed a real weakness (a scrape lacking columns leaked NULLs from the stored side), fixed by the `LISTING_COLUMNS` validation plus an allow-list of written columns in the insert and update paths.
- **3.3.4 — Test coverage.** Mapping the roadmap's scenarios onto existing tests found one real gap (a non-price change must stay "unchanged"); closed in #21. "Zero writes on re-run" was redefined: no new price-history entry and no content change; only `last_seen_at` moves (tested end to end).
- A V2 idea was parked: full field-level change history.

**3.4 — Price-Change Tracking — done (code)**
- **3.4.1 — Price deltas (PR #19).** `compute_price_deltas()` in `price_events.py`: euro and percent change for modified listings; division-by-zero guarded (old price 0 → no percentage); no rounding in code (Postgres stores ~15 significant digits).
- **3.4.2 — Price-change events (PR #20).** One append-only row per modified listing; `id` and `detected_at` are DB defaults. Reworked in 3.3.3 so the event can join the update's transaction (`write_price_change_events`, with `insert_price_change_events` kept as a thin standalone wrapper that the pipeline should not use).
- **3.4.3 — End-to-end coverage (PR #22).** Mapping the roadmap's four cases found two gaps (an increase end to end; two successive drops). Added: increase, two successive drops chaining correctly, and a flat day between drops adding nothing. Mutation-checked.
- **3.4.4 — Delisting detection and handling (PR #24).** Pulled into V1 (it was scoped V2). `mark_delisted_listings()` in `delist.py` writes `delisted_at` = the day the run concluded the listing was gone, once only (guarded in Python and by `delisted_at IS NULL` in the UPDATE). `update_listings` now clears `delisted_at` for any listing seen again and reports `listings_reinstated`. Verified on real Supabase over five simulated days.

**Housekeeping PR #23:** pytest restricted to `tests/` (`[tool.pytest] testpaths`) and the SQLite datetime warning removed from `test_insert.py`.

**3.5.0 — Make DVF fetch complete and fail loudly — done (PRs #26 and #27).** New roadmap task, numbered 3.5.0 so it sorts before 3.5.1 without renumbering. Notion page: https://app.notion.com/p/40750849ad7e819cb151e0ebb67466d5.
- **PR #26 — complete or fail.** The default cap of 10 pages (100 rows each) had silently cut Carqueiranne from 3,159 mutations to 1,000. `fetch_mutations` now reads the API's own `count` on the first page, derives its page ceiling from it (plus a margin of 2 pages that only guards against a runaway loop), drops duplicate rows by `idmutation`, and raises `IncompleteFetchError` if the ceiling is hit with pages pending, if `count` is missing, or if the distinct rows fetched do not match `count`. `allow_partial=True` is an explicit opt-in for sampling (used by scratch scripts and fixture capture); the orchestrator passes `max_pages_per_commune` (default `None`) and `allow_partial` through. Progress is logged every 10 pages. 13 new tests on fake pages, mutation-checked in 7 ways. Real API: Le Revest (773) and Carqueiranne (3,159) matched the API's count exactly; a deliberately low ceiling raised.
- **PR #27 — patience on the first request only.** The first request of each commune now has a 65 s timeout and up to 5 attempts (`FIRST_REQUEST_TIMEOUT_SECONDS`, `FIRST_REQUEST_MAX_ATTEMPTS`); later pages keep 15 s and 3 attempts. `_get_with_retry` gained a `max_attempts` option. 8 new tests (`tests/test_dvf_retry.py` plus one extended), mutation-checked; one mutation initially survived and exposed a test gap (every attempts value used happened to equal the old default), fixed. Real API: four probably-cold communes returned their first page in 83 s (after one retry), 36 s, 18 s and 21 s.
- **Settled by the full loads (3–4 Nov 2026):** a cold Toulon, Hyères, La Seyne and Six-Fours all succeeded within the 5 first-request attempts, and the count check passed on all 24 full walks (see the API observations below). The thinnest margin was Hyères, which needed 4 of 5 attempts.

**3.5 — DVF Load into Supabase — done (PRs #28, #29, #30; completed 4 Nov 2026).** Notion: step page https://app.notion.com/p/3be50849ad7e816a9e68c5dd5dbc8308 (summary written 4 Nov); the task pages 3.5.1–3.5.3 carry the details and dated amendments.
- **3.5.1 + 3.5.2 — the loader (PR #28).** `load_transactions(cleaned, engine, batch_size=1000)` in `dvf/load.py` upserts ONE commune's cleaned DataFrame by `id_mutation`, as read → compare → write inside one transaction (through the shared `run_in_transaction`), and returns `LoadSummary(inserted, updated, unchanged)`. Per batch of 1,000 rows it reads the stored rows, classifies each incoming row as new / changed / unchanged, inserts the new ones and updates the changed ones; it never deletes. Validation runs before anything is written: `TRANSACTION_COLUMNS` (derived from the `Transaction` dataclass fields), `NULLABLE_TRANSACTION_COLUMNS = ("price", "rooms")` and `require_transaction_columns` live in `dvf/models.py`; a frame with a missing column, a duplicate `id_mutation` or a null in a NOT NULL column is refused, with the column and ids named. Only the 13 source columns are written (allow-list). NaN becomes a real NULL (object cast first). Every value is converted to a plain Python type (`rooms` is `3`, not `3.0`; a non-whole room count is refused). The comparison normalises Decimal (Postgres `numeric`) and float to a float rounded to 6 decimals, and None/NaN to None (insurance: a float round-trips exactly through numeric; pinned by a test). Checked on real Supabase with Le Revest (773 rows): first load inserted 773, an identical reload changed nothing, one revised price updated exactly one row, cleanup done.
- **Runner (PR #29).** `dvf/runner.py` (`load_communes`, `format_report`, `has_failures`, `validate_commune_codes`) and `scripts/load_dvf.py`: one commune at a time, each in its own transaction, with a 1.5 s pause between communes. An empty fetch is skipped (`clean_transactions([])` raises `KeyError: 'price'`). Any other failure (fetch, validation, database) is recorded with its commune code and error text (cut at 500 characters) and the run continues; the exit code is 1 if any commune failed, and the report prints the re-run command. Ctrl-C still stops the run. Only the twelve known communes are accepted (typo guard). Usage: `poetry run python scripts/load_dvf.py [codes]` (no codes = all twelve). Checked on real Supabase with Le Revest and Le Pradet (3,853 rows, Le Pradet in 4 batches): the first run inserted everything and an identical re-run changed nothing.
- **Full load.** First load, 3–4 Nov 2026 (two communes, then six, then four; about 14 + 55 minutes): 125,569 mutations fetched, exactly the API's own total, and 125,353 rows stored (216 mutations were returned by two communes and stored once; the second commune reported them unchanged). **Second full load** (one command, no codes, 22:31–23:45 on 4 Nov, 74 minutes): 0 inserted, 0 updated and 125,569 unchanged on all twelve communes, exit code 0, and Postgres still held 125,353 rows. No commune failed and no NaN reached a NOT NULL column.
- **3.5.3 — tests.** `tests/test_dvf_load.py` (36 cases: pure preparation/comparison tests plus database tests on in-memory SQLite) and `tests/test_dvf_runner.py` (16). 193 tests in total on `main`. Both files were mutation-checked (loader: 17 mutants in a sandbox plus 5 by hand; runner: 15 plus 5 by hand). One loader mutant survived the first round, the rounding in the comparison, and an assertion now pins it. A first draft of the revised-row test only changed the price, so it would not have caught a loader that compared only the price; a parametrised test now revises each of the 12 value columns.
- **PR #30.** The real first-request failure is HTTP 502 (Proxy Error) after about 60 s, not the 504 the test fakes assumed; the fakes now copy the real message and the helper in `tests/test_dvf_retry.py` is called `proxy_error`.

**What the `transactions` table holds (verified 4 Nov 2026):** 125,353 rows and 125,353 distinct `id_mutation`; sales from 2014-01-02 to 2025-12-31; every `year` equals the year of its `date`; no negative price or surface; 57 rows with no price (0.05%); 558 with a price under 2 euros (0.45%), so `price >= 2` leaves out 615 rows (0.49%); 23,481 bare-land rows, `surface_bati = 0` (18.7%); 45,942 rows with rooms (36.7%), maximum 5 ("5 or more"); 49 rows (0.04%) whose primary `commune_code` is outside the twelve (17 other communes, 29 distinct primary communes in total). `commune_code` is the mutation's primary commune (`l_codinsee[0]`), not the commune that was queried; the Toulon code (83137) holds 47,213 rows. The table is 19 MB including indexes (the rough 25 MB estimate was close) against the 500 MB free-tier cap. It stores no address or neighbourhood, only the commune.

**Real DVF scale (API-reported counts):** Toulon 47,296 · Hyères 18,108 · La Seyne 17,859 · Six-Fours 13,529 · La Valette-du-Var 6,320 · La Garde 6,080 · La Crau 3,843 · Carqueiranne 3,159 · Le Pradet 3,080 · Ollioules 3,023 · Saint-Mandrier 2,499 · Le Revest 773. **Total 125,569** (a mutation spanning two communes counts in both: 216 such overlaps were found, hence 125,353 stored rows), about 1,260 pages, 70–75 minutes for a full load. The counts were identical on 24 Oct, 3 Nov and 4 Nov (both full loads), which suggests no new DGFiP/Cerema refresh in that period (an inference).

**What the DVF+ API actually does (observed in two full loads, 3–4 Nov 2026):**
- The first request for a commune is slow and highly variable. When it fails it is an HTTP 502 `Proxy Error` after almost exactly 60 s (60.2 s each time, before the 65 s client timeout can trigger), or occasionally a 65 s client read timeout. The next attempt then succeeds in 13–53 s. That is consistent with the server finishing its work after the proxy gave up, but it is not proven. The same commune varies a lot between runs (Carqueiranne 19 s then 52 s; La Crau 22 s then 67 s; Hyères 90 s then 204 s; Toulon about 3 minutes then 88 s). Communes of 2,500–6,300 rows answered their first page in 15–33 s in the first load; the four biggest all exceeded 60 s at least once.
- Once answered, the same request is fast: on 3 Nov the Toulon request that had failed twice answered in 0.6 s five times in a row a few minutes later, and Le Revest and Le Pradet answered their first page in 0.65 s and 0.5 s about four minutes after cold responses of 15.5 s and 54.7 s.
- Retry budget in practice: in the first full load four communes needed more than one first-request attempt (Six-Fours, La Seyne, Hyères: 2; Toulon: 3); in the second, six of twelve did (La Crau, La Garde, La Valette-du-Var: 2; Toulon: 2; Six-Fours: 3; Hyères: 4 of the 5 allowed, the thinnest margin seen). No commune exhausted its attempts.
- Mid-walk pages take about 2.1–2.4 s end to end (10 pages in 21–24 s): the request itself answers in about 0.5 s, and the rest is consistent with the client's 1.5 s courtesy pause. 15 s read timeouts are frequent and always absorbed (never beyond attempt 2 of 3). The average is about 2.7–3.3 s per page including timeouts.
- Pagination order is not stable across calls, so the `count` check is the safety net; it passed on all 24 full walks (no `IncompleteFetchError`).
- The response carries a `count` field (total mutations for the query) and 100 rows per page.
- Unexplained and harmless: one attempt (Six-Fours, second load) logged a 65 s read timeout after only about 31 s.
